# Подписки на озвучку/балансер

Как устроена подписка на новые серии в yani. Главное: **состояние подписки отдаёт сам сервер в
списке
видео** — восстанавливать его по названиям озвучек не нужно и невозможно.

## Контракт API

### `GET /anime/{id}/videos`

Плоский список: **одна запись = серия × озвучка × балансер**.

```json
{
  "video_id": 1027521,
  "number": "1",
  "data": {
    "player": "Плеер Kodik",
    "dubbing": "Озвучка РуАниме / DEEP",
    "player_id": 4
  },
  "watched": {
    "end_time": 1336,
    "date": 1784061705
  },
  "subscribed": true,
  "iframe_url": "…"
}
```

* `player_id` стабилен: `2` Alloha, `3` CVH, `4` Kodik, `7` Sibnet, `8` VK. **У озвучки
  идентификатора
  нет — только название.**
* **`subscribed`** — подписан ли пользователь на новые серии этой озвучки и балансера. Поле приходит
  только авторизованному пользователю (в публичном ответе его нет вовсе), стоит у всех серий группы
  и
  является единственным достоверным источником состояния. Рядом с ним живёт такой же
  пользовательский `watched`.

### `PUT | DELETE /video/{video_id}/subscribe`

Тела запроса нет, ответ — `{"response": true}`. `video_id` — любая серия нужной озвучки: сервер сам
сводит
её к тройке «тайтл + балансер + озвучка». Официальный веб-клиент шлёт `video_id` серии, открытой в
плеере.

Проверено вживую: две подписки на разные озвучки одного балансера дают **две** записи, `DELETE`
удаляет
ровно одну. Приложение отписывается тем видео, у которого сервер сам проставил `subscribed`.

### `GET /users/{userId}/lists/subs`

```json
{
  "sub": {
    "dubbing": "",
    "player": "Kodik",
    "player_id": 4
  },
  "anime_id": 26429,
  "anime_url": "tabakoshka",
  "title": "…",
  "poster": {
    …
  }
}
```

Список всех подписок пользователя — по строке на подписку. Используется **только** экраном
«Мои подписки» (первый пункт вкладки уведомлений). Для состояния конкретной озвучки не годится:

* **`sub.dubbing` не сообщает озвучку подписки.** Приходит либо пустым, либо `null`, либо
  перечислением
  всех озвучек этого балансера — `"AniLibria() AniDUB() SHIZA Project() … "` — одинаковым у всех
  подписок
  одного балансера. Из-за `null` в non-null поле с дефолтом разбор ответа падал целиком, пока в
  `YaniApiJson` не включили `coerceInputValues` (регресс закрыт `YaniSubscriptionsParsingTest`).
* `sub.player` — короткое имя (`"Kodik"`), тогда как в списке видео оно приходит как
  `"Плеер Kodik"`.
* `video_id` и номера серии в ответе нет вовсе.
* `anime_id` и `player_id` приходят то числом, то строкой — отсюда `JsonElement` в DTO.

## Как это работает в приложении

1. `SubscriptionOptionMapper` группирует видео по `SubscriptionKeys.subscriptionKey(...)`
   (плеер по `player_id`, озвучка по нормализованному названию) и берёт `isSubscribed` из
   `videos.any { it.isSubscribed }`.
2. Пока запрос в полёте, кнопка показывает оптимистичное значение из `pendingStates`
   в `DetailsSubscriptionHandler` — записи живут только на время мутации.
3. После успешного `PUT|DELETE` вызывается `RefreshAnimeVideosUseCase`: кэш видео живёт 5 минут, и
   без
   принудительного перезапроса галочка вернулась бы в прежнее состояние.
4. При выходе из аккаунта кэш видео помечается устаревшим (`AnimeStorage.expireAllVideos()`) —
   `watched`
   и `subscribed` в нём принадлежат прежнему пользователю.

## Чего делать не надо

Сравнивать `sub.dubbing` из `/lists/subs` с названиями озвучек из `/videos` — в любом виде, включая
«мягкое» сравнение по вхождению подстроки. Именно так и было сделано раньше: перечисление всех
озвучек
балансера подходило под каждую строку списка, и подписка на одну озвучку подсвечивала весь балансер.
На реальных данных вхождение подстроки ломается и само по себе: «Субтитры» ⊂ «Субтитры Wakanim»,
«Озвучка AniDUB» ⊂ «Озвучка AniDUB Online», «Озвучка Kansai» ⊂ «Озвучка KANSAI Studio».

Хранить выбранную озвучку локально тоже не нужно: такая таблица знала бы только о подписках,
оформленных
в этом приложении, и не видела бы сделанных на сайте или до её появления.
