# Подписки на озвучку/балансер

Как устроена подписка на новые серии в yani и почему приложение хранит часть состояния локально.

## Контракт API

Подписка живёт на уровне «тайтл + балансер + озвучка», но в API нет ни одного поля, которое бы эту
тройку называло целиком.

### `GET /anime/{id}/videos`

Плоский список: **одна запись = серия × озвучка × балансер**.

```json
{
  "video_id": 196228,
  "number": "24",
  "data": { "player": "Плеер Kodik", "dubbing": "Озвучка AniLibria", "player_id": 4 },
  "iframe_url": "…"
}
```

`player_id` стабилен: `2` Alloha, `3` CVH, `4` Kodik, `7` Sibnet, `8` VK.
**У озвучки идентификатора нет — только название.** Признака «подписан» в ответе тоже нет.

### `PUT | DELETE /video/{video_id}/subscribe`

Тела запроса нет, ответ — `{"response": true}`. `video_id` — любая серия нужной озвучки: сервер сам
сводит её к тройке «тайтл + балансер + озвучка». Официальный веб-клиент шлёт `video_id` серии,
открытой
в плеере в этот момент.

Проверено вживую: две подписки на разные озвучки одного балансера дают **две** строки в списке
подписок,
а `DELETE` удаляет ровно одну из них.

### `GET /users/{userId}/lists/subs`

```json
{
  "sub": { "dubbing": "", "player": "Kodik", "player_id": 4 },
  "anime_id": 14388, "anime_url": "…", "title": "…", "poster": { … }
}
```

Здесь и находится главный подвох:

* **`sub.dubbing` не сообщает озвучку подписки.** Он приходит либо пустым, либо перечислением всех
  озвучек этого балансера — `"AniLibria() AniDUB() SHIZA Project() … "` — и это перечисление
  одинаково
  у всех подписок одного балансера. Восстановить по нему выбор невозможно.
* `sub.player` — короткое имя (`"Kodik"`), тогда как в списке видео оно приходит как
  `"Плеер Kodik"`.
* `video_id` и номера серии в ответе нет вовсе.
* `anime_id` и `player_id` приходят то числом, то строкой — отсюда `JsonElement` в DTO.

## Что из этого следует для приложения

Сопоставлять подписку с озвучкой по названию **нельзя** — сопоставлять не с чем. Поэтому:

1. Выбранная озвучка и `video_id`, которым оформлена подписка, сохраняются локально —
   таблица `video_subscription_selection` (`core:storage`), ключ
   `(userId, animeId, playerKey, dubbingKey)`.
   Ключи строит `SubscriptionKeys` (`feature:account:domain`): плеер — по `player_id`, с запасным
   вариантом по имени со снятым префиксом «Плеер »; озвучка — по нормализованному названию.
2. Отписка идёт сохранённым `video_id`, а не «последней серией озвучки»: набор серий со временем
   меняется, и такой идентификатор нестабилен.
3. `/users/{id}/lists/subs` используется как счётчик: сколько подписок реально есть на каждом
   балансере
   тайтла. `GetAnimeSubscriptionStateUseCase` сверяет с ним локальные записи и выбрасывает лишние —
   так подхватывается отписка, сделанная на сайте или на другом устройстве.

Ограничение, которое из API не обойти: подписку, оформленную **вне приложения**, привязать к
конкретной
озвучке нельзя — сервер не говорит, к какой именно. Такая подписка в списке озвучек не подсветится.

## Чего делать не надо

Сравнивать `sub.dubbing` с названиями озвучек из `/videos` — в любом виде, включая «мягкое»
сравнение
по вхождению подстроки. Именно так и было сделано раньше: перечисление всех озвучек балансера
подходило под каждую строку списка, и подписка на одну озвучку подсвечивала весь балансер. На
реальных
данных вхождение подстроки ломается и само по себе: «Субтитры» ⊂ «Субтитры Wakanim»,
«Озвучка AniDUB» ⊂ «Озвучка AniDUB Online», «Озвучка Kansai» ⊂ «Озвучка KANSAI Studio».
